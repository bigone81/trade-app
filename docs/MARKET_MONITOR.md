# Market Monitor — Phase 1

Market Monitor доступен по `/market-monitor`: текущие наблюдения, лента истории,
объяснение оценок, настройки и watchlist. Переход к графику выбирает символ;
цена уровня передаётся в URL, отдельной подсветки выбранного уровня пока нет.
Мониторинг и Telegram по умолчанию выключены.

## Архитектура

- `packages/shared/src/market-monitor.ts`: типы, числовые ограничения и defaults.
- `packages/domain/src/market-monitor.ts`: признаки, оценки, выбор монет,
  кластеризация уровней и антиспам.
- `packages/database/src/market-monitor.ts`: идемпотентная инициализация SQLite
  и хранение настроек, watchlist, состояний, наблюдений, текущих монет и heartbeat.
- `apps/api/src/market-monitor.ts`: API под существующей авторизацией приложения.
- `apps/market-worker`: отдельный процесс с публичными данными Bybit,
  очередью запросов, кешем старших ТФ и арендой в SQLite для одного владельца.
- `packages/database/src/telegram.ts`: общий транспорт уведомлений для обоих
  workers. Существующий торговый worker использует тот же транспорт.

Торговые операции Market Monitor не выполняет. Анализ запускается после закрытия
M5 с задержкой 5 секунд. Старшие ТФ обновляются при смене свечи. Автоуровни
вычисляются существующим `detectLevels` из 30 дневных свечей, как на графике,
включая открытую дневную свечу. Этот вход обновляется каждый цикл M5.
Для исторических касаний отдельно загружается до 400 дневных свечей.
Пропущенные или устаревшие M5 дают ошибку монеты; последнее наблюдение остаётся
видимым с его временем и пометкой ошибки.

## Нагрузка Bybit и восстановление

Все публичные REST-запросы Market Worker проходят через одну очередь
`apps/market-worker/src/request-queue.ts`: M5, H1, H4, D1, страницы инструментов
и общий список тикеров. Старый интервал 100 мс позволял около 10 стартов/с;
после ответа об ограничении очередь продолжала отправлять остальные запросы.
Кроме того, прежняя обёртка свечей/тикеров сохраняла только текст ошибки,
теряя `retCode` и время сброса лимита.

Теперь минимальный интервал между фактическими стартами — **350 мс**
(около **2,86 запроса/с**). После простоя накопленные запросы не стартуют пачкой.
Новая настройка concurrency по умолчанию — 2; уже сохранённые значения 1–5
сохраняются. Ограничение скорости действует независимо от concurrency.
Ожидания выполняются асинхронными таймерами, heartbeat продолжает работать.

Отдельный клиент без ключей и доступа к счетам использует существующий SDK
`bybit-api` с таймаутом запроса 15 секунд и `parseAPIRateLimits`.
Проверенная установленная версия SDK не повторяет REST-запросы автоматически.
Обёртка `public-data.ts` сохраняет код ошибки и метаданные лимита.
Преобразование свечей соответствует адаптеру графика.

Обрабатываются `retCode: 10006`, HTTP 429, сообщения `Too many visits` /
`Exceeded the API Rate Limit`. HTTP 403 сам по себе не считается Rate Limit.
Только явно указанное `403 access too frequent` трактуется как IP-бан:
Market Worker откладывает запросы минимум на 10 минут. Эти ответы и семантика
`X-Bapi-Limit-Reset-Timestamp` описаны в
[правилах Bybit](https://bybit-exchange.github.io/docs/v5/rate-limit);
HTTP 429 также указан в [списке ошибок](https://bybit-exchange.github.io/docs/v5/error).

При Rate Limit:

1. Вся очередь прекращает новые старты; уже выполняющиеся запросы завершаются.
2. Паузы растут: 3, 10, 30 секунд плюс jitter 0–249 мс. Будущий timestamp
   сброса и корректный `Retry-After` могут увеличить паузу.
3. Интервал стартов удваивается, максимум до 1400 мс. После минимум
   20 успешных ответов и 30 секунд успешной работы он сокращается на 20%,
   постепенно возвращаясь к 350 мс.
4. На один запрос разрешено максимум 3 повтора. Четвёртый ответ об ограничении
   в цикле, суммарный бюджет пауз свыше 60 секунд или выход за срок M5
   откладывает оставшуюся часть цикла. Очередь не создаёт ошибку на каждую монету.
   Длинный reset/IP-бан откладывает цикл сразу, сохраняя паузу для следующих циклов.

Пауза и сниженная скорость сохраняются между циклами в памяти процесса,
но не переживают перезапуск контейнера. Повторы существуют только в очереди
публичного чтения Market Worker. Создание, изменение, отмена, закрытие ордеров,
SL/TP/Trailing Stop и приватные WebSocket этой очередью не обслуживаются.

## Безопасность циклов и кеш

SQLite lease защищает от второго worker; `busy` в worker и защита scanner
не допускают параллельных циклов. Бюджет цикла — максимум 240 секунд и не позже
начала следующей M5. Уже начатый REST-запрос/Telegram может завершаться ещё
до 15 секунд; новые запросы/сигналы после срока не запускаются. Scanner ждёт
завершения своих запросов перед освобождением цикла.

Проверяются последняя закрытая M5 монеты и BTC, непрерывность последних 30 M5,
актуальность закрытых H1/H4/D1 и открытой D1 для автоуровней. Просроченный
цикл получает `DEGRADED` с причиной `Market scan deferred`, старые строки
не получают новую отметку свежести. Следующий доступный цикл анализирует
актуальную закрытую M5; пропущенные свечи не проигрываются задним числом.
Завершённая монета для той же M5 повторно не анализируется, в том числе
после перезапуска. Существующие уникальность наблюдений, состояния антиспама
и дедупликация уведомлений остаются дополнительной защитой; повторной
отправки уже созданных Telegram-уведомлений после восстановления нет.

Ключ кеша: символ + интервал + размер набора + временной bucket:

| Данные | Когда обновляются |
| --- | --- |
| M5, 310 свечей | Каждый цикл M5; BTC загружается один раз для всех монет |
| H1, 80 свечей | При смене часа |
| H4, 80 свечей | При смене четырёхчасового периода |
| D1, 400 свечей для истории | При смене дня |
| D1, 30 свечей для автоуровней | Каждый M5, включая текущую открытую дневную свечу |
| Инструменты и тикеры universe | По настройке 10–15 минут или при изменении состава/настроек |

Одновременные идентичные запросы свечей используют один Promise.
Наборы D1/30 и D1/400 намеренно не объединены: у них разное назначение
и момент обновления. `detectLevels`, ATR, признаки, баллы и сценарии не изменены.

## Серверная диагностика

События JSON: `market-monitor.rate-limit`, `market-monitor.backoff-start`,
`market-monitor.backoff-end`, `market-monitor.request-retry`,
`market-monitor.scan-deferred`. Записываются категория (`instruments`, `tickers`,
`kline:<интервал>:<размер>`), распознанная причина/код, номер повтора, пауза
и текущая разрешённая скорость. Исходные объекты ошибок SDK, ключи,
токены и параметры приватных запросов в эти логи не выводятся.

`market-monitor.cycle` сохраняет `symbolsScanned`, `requestsMade`,
`cycleDurationMs`, `errors`, `signalsDetected`, `alertsSent` и дополнительно
выводит `rateLimitHits`, `retryCount`, `backoffMs`, `effectiveRps`,
`requestsSucceeded`, `requestsFailed`. Счётчики REST учитывают все фактические
попытки, включая повторы. `errors` — ошибки анализа/отложенный цикл;
`requestsFailed` — неудачные REST-попытки, даже если повтор затем прошёл.
`backoffMs` — фактически прошедшее время общей паузы в текущем цикле,
без двойного учёта параллельных ответов. `effectiveRps` — текущий потолок
очереди; наблюдаемая средняя скорость равна `requestsMade / cycleDurationMs * 1000`.
Новые поля хранятся в существующем runtime JSON, миграция SQLite не нужна.

## Ожидаемая длительность и границы ограничения

Оценки при интервале 350 мс, без Rate Limit и больших задержек сети/Telegram:

| Цикл | 37 монет | 100 монет |
| --- | --- | --- |
| Обычный M5 с прогретым кешем | около 25–30 с | около 70–80 с |
| С обновлением H1 | около 38–45 с | около 105–115 с |
| Холодный старт: все 5 наборов | около 65–75 с | около 175–190 с |

Основа оценки: примерно `2N + 1` запросов в обычном цикле, `3N + 1` при H1,
`5N + 1` при холодном старте, плюс страницы инструментов/тикеры при обновлении
universe. BTC в списке, ручной режим и кеш могут уменьшать число запросов.
Для наблюдавшихся 71/108 запросов само распределение стартов занимает
24,5/37,45 секунды. H4 и смена дня увеличивают нагрузку; backoff и медленные
ответы увеличивают время и могут отложить остаток анализа до следующей M5.

Ограничение локально для Market Worker. API отдельно получает публичные
тикеры, свечи, уровни, ATR и правила инструмента (их кеш — 10 минут).
График опрашивает тикеры каждые 10 секунд, свечи каждые 5 минут;
ордера/позиции — каждые 5 секунд, исполнения — каждые 30 секунд.
Торговый worker получает цены и исполнения через публичные/приватные WS.
Эти источники и торговые запросы API не изменены.

Общий исходящий IP может использоваться другими процессами/клиентами.
Поэтому отсутствие внешних лимитов нельзя гарантировать только этой очередью.
Общая координация между контейнерами потребовала бы отдельного сервиса или
общего диспетчера с приоритетом торговых операций; в это изменение она не входит.
Production-проверка фактической нагрузки выполняется отдельно после разрешения
на деплой, без изменения `.env`, данных и Docker volumes.

## Хранение истории: 72 часа

`packages/database/src/market-retention.ts` экспортирует `cleanupMarketSignals`.
Граница фиксируется один раз на начало задания: `UTC now − 259200000 мс`
(ровно 3 × 24 часа). Используется существующее `created_at`, записанное SQLite
как UTC `YYYY-MM-DD HH:mm:ss`. Удаляются только строки с `created_at < cutoff`:
ровно на границе и более новые строки остаются. Погрешности округления секунды
при сравнении TEXT учтены; структура JSON не меняется. Фильтров по типу сигнала,
приоритету или отправке уведомления нет.

Планировщик зарегистрирован **только в API/app**, после начала прослушивания
HTTP, и повторяет запуск каждый час независимо от настроек Market Monitor.
Следовательно, запись, пересёкшая границу между запусками, удаляется при
следующей успешной очистке; физическое хранение может составить около 73 часов
или дольше при ошибках/блокировке. `worker` и `market-worker` очистку не запускают.
При существующей конфигурации Compose работает один экземпляр `app`;
перед масштабированием API понадобится координация между экземплярами.

Каждое задание создаёт временный Node.js worker thread внутри `app` с отдельным
соединением к существующей базе. Это не Docker-сервис. Поток завершает работу
и закрывает соединение после задания; синхронный `node:sqlite`, включая первое
создание индекса, не занимает event loop HTTP-сервера. Лимит old-generation
V8 этого потока — 32 МиБ, кеш SQLite — примерно 2 МиБ, временная сортировка
разрешена на диске; это не жёсткий лимит всей нативной памяти процесса.

Удаление выполняется по 250 строк одним параметризованным DELETE на порцию,
в autocommit, с освобождением event loop между порциями. Общей транзакции на
всю историю нет. Повторные вызовы на одном соединении присоединяются к текущему
заданию; планировщик также не запускает второй поток до завершения первого.
На первом запуске создаётся `idx_market_signals_created_at ON market_signals(created_at)`.
Это однократная операция: построение индекса требует места и блокировки записи,
поэтому первый production-запуск нужно планировать с учётом текущей нагрузки.

При `SQLITE_BUSY`/`SQLITE_LOCKED` ожидание блокировки в соединении очистки
ограничено 100 мс. Задание заканчивается с диагностикой, ранее удалённые порции
сохраняются, следующая попытка — через час. Ошибки открытия/чтения/удаления
и ошибки потока обрабатываются без остановки API. При закрытии API таймер
отключается, активному заданию передаётся остановка; завершение текущей порции
и закрытие соединения ожидаются до закрытия основной базы. SIGTERM/SIGINT
запускают этот путь завершения Fastify.

Событие лога приложения `market-monitor.retention` содержит `startedAt`,
`cutoffAt`, `deletedRows`, `batches`, `durationMs`, `stopped`, `error`.
Ошибка содержит безопасный код и числовой код SQLite, без текста SQL/JSON,
токенов и данных уведомлений. При аварии самого потока точный счётчик неизвестен:
в таком случае `deletedRows: null`, а не ошибочное утверждение о нуле удалений.

`notifications`, журнал сделок, исполнения, `system_events`, состояния Market
Monitor, текущие символы, watchlist и настройки не очищаются. Удаление не
сбрасывает AUTOINCREMENT, ключи уведомлений или состояния антиспама.
`VACUUM`, принудительный checkpoint, удаление файлов и пересоздание таблиц
не выполняются. Освободившиеся страницы SQLite используются повторно;
немедленное уменьшение файла базы не ожидается.

### Безопасный production deployment

Локальная сборка и тесты не заменяют проверку production. До разрешённого
деплоя нужно:

1. Проверить свободное место и inode на файловых системах базы, backup,
   временных файлов и Docker. Учесть размер всей SQLite, текущего WAL,
   отдельной резервной копии, нового индекса и сборки образов. 85 МБ одной
   таблицы недостаточно для оценки; при нехватке места деплой остановить.
2. Проверить наличие актуальной **консистентной** резервной копии и путь
   восстановления. Для работающей WAL-базы использовать SQLite Online Backup
   API (`node:sqlite` `backup()` / SQLite `.backup`), а не копировать один
   `trade.sqlite` без WAL. Проверить копию через `PRAGMA integrity_check`
   (`ok`) и контрольные количества записей; сохранить её отдельно от рабочей БД.
   См. [SQLite Online Backup](https://www.sqlite.org/backup.html).
3. Согласовать push и deploy: `AGENTS.md` связывает успешный push в main
   с запуском `deploy.ps1`, но production требует отдельного разрешения.
4. После подтверждения выполнить канонический `deploy.ps1` и проверить
   `app` healthy, работу обоих workers и событие `market-monitor.retention`.
   Первая очистка начнётся автоматически после запуска обновлённого API.

Проверки выполняются без изменения production `.env`, удаления данных,
Docker volumes или принудительного освобождения диска через prune.

## Настройки и уведомления

Стартовые значения: HYBRID, оборот входа $50 млн / выхода $40 млн,
максимум 100 автоматических монет, обновление списка раз в 15 минут.
Watchlist и монеты с ручными уровнями добавляются отдельно; общий список
дедуплицируется и ограничивается активными USDT perpetual Bybit.
Монеты ниже порога оборота, добавленные только через ручные уровни, анализируются
только по ручным уровням. Участники Auto сохраняют автоуровни до порога выхода
($40 млн по умолчанию); после выхода возвращаются в Auto только при достижении
порога входа ($50 млн). Watchlist разрешает анализ всех уровней независимо от
оборота. Для монет с оборотом не ниже порога входа автоуровни также сохраняются,
даже если монета не вошла в Auto из-за лимита количества.
Признаки дают отдельные оценки Approach, Breakout и Rejection. Пороги и веса
редактируются в расширенных настройках; это инженерные начальные значения.

Повторные уведомления ограничиваются состоянием `(symbol, level, scenario)`,
паузой 30 минут, ростом оценки на 3 или уходом дальше 1.5 ATR и новым подходом.
Наблюдения сохраняются независимо от отправки; уникальность
`(symbol, level_key, bar_time)` предотвращает дубли после перезапуска.
`market_signals.notified` означает создание уведомления внутри приложения.
Фактический результат Telegram находится в `notifications.telegram_status`.
Отправка требует настройки самого монитора, глобального `telegramMarket`,
токена/чата и минимального приоритета HIGH. Telegram включён только для
FAST_APPROACH, BREAKOUT_SETUP и REJECTION_SETUP; результаты пробоя остаются
в истории и внутренних уведомлениях. Автоматической очереди повторной отправки нет.
В Telegram добавлена ссылка «Открыть график» с символом и ценой уровня; подпись
использует выбранный язык en/ru/uk. Адрес берётся из `PUBLIC_APP_URL` (публичный
адрес EdgeDesk); если он не задан или некорректен, сообщение отправляется без ссылки.

## API

Префикс `/api/market-monitor`:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / PUT | `/settings` | Получение / частичное обновление настроек |
| GET / POST | `/watchlist` | Список / добавление или переключение монеты |
| DELETE | `/watchlist/:symbol` | Удаление монеты |
| GET | `/status`, `/symbols` | Состояние worker и текущие наблюдения |
| GET | `/signals` | История: `symbol`, `before`, `limit`, `signalsOnly` |
| GET | `/signals/:id` | Одно наблюдение |

## Локальная проверка

Из корня репозитория, Node.js 24 и pnpm из `packageManager`:

```powershell
corepack pnpm build
corepack pnpm test
```

Build включает TypeScript всех пакетов. Тесты используют синтетические свечи,
SQLite в памяти, Fastify injection и подменённый fetch для Telegram.
Рабочий запуск входит в `corepack pnpm dev`; отдельно:
`corepack pnpm --filter @trade/market-worker start` после сборки.

Для проверки интерфейса без биржи и базы:

```powershell
node apps/web/tests/fixtures/market-monitor-preview.mjs
```

Открыть `http://127.0.0.1:4180/market-monitor?preview=live`.
Режимы `empty`, `disabled`, `error`, `loading` проверяют соответствующие состояния.
Изменения preview хранятся только в памяти процесса.

В Compose добавлен `market-worker` с общей SQLite и проверкой heartbeat.
Production deployment выполняется только каноническим `deploy.ps1` после
отдельного разрешения. Перед рабочим включением нужно проверить контейнер,
полный цикл на реальных данных и, при необходимости, доставку Telegram.

## Границы Phase 1

ТВХ1/2/3 зарезервированы в типах. Сложные БСУ/БПУ, U-formation, заражённая зона
и distribution требуют отдельной формальной модели и остаются для Phase 2.
Наблюдения не являются результатами бэктеста. История `market_signals` хранится
72 часа с почасовой очисткой; долговременный архив наблюдений не создаётся.
